# 多节点线路选择（大陆 / 香港）

- 日期：2026-09-23
- 分支：`feat/cuberouter-login`
- 状态：设计已定，待写实施计划
- 相关：`docs/superpowers/plans/2026-09-18-cuberouter-followups.md` 的 **F1**（`config.yaml` 存 cuberouter 地址）与 **F2**（manifest 注入）

## 1. 问题与目标

后端在同一套代码上部署了两处，API 完全一致、域名不同：大陆（`test.cuberouter.cn`，后续将改为 `cuberouter.cn`）与香港（`cuberouter.com`）。希望用户自动连到合适的那一个。

**关键约束（决定了整个设计）：两处账号数据各自独立。** 同一个用户名在两边是两个不同的账号。因此：

- **线路是账号的属性，不是网络的属性。** 线路在**注册那一刻**定下来，之后登录必须回到同一节点，否则用户会看到"账号不存在"。
- **不能按请求自动切换。** A 节点不可用时把用户"自动切到 B"等于告诉他账号没了。
- 能自动的只有一件事：**首次注册时选哪个节点**；以及找不到归属时的兜底尝试。

**因此要解决的不是"识别地理位置"，而是"判断哪个节点可用、且账号在哪边"。** IP 归属地查询在大陆恰恰最脆弱（查 IP 的服务本身可能连不上，VPN 用户还会判错），只作为最后兜底。

**非目标**：跨节点账号搬家/数据同步；GeoDNS；每次请求动态切线路；把两地数据打通。

## 2. 实测结论（2026-09-23，从大陆网络）

| 节点 | DNS | TCP 连接 | TLS | TTFB | `GET /api/status` |
|---|---|---|---|---|---|
| `cuberouter.com` | 7–14ms | 237–310ms | 334–406ms | 395–633ms | 200 + JSON |
| `test.cuberouter.cn` | 6–13ms | 38–48ms | 82–95ms | 117–131ms | 200 + JSON |
| `cuberouter.cn`（未部署） | 7–34ms | 37–143ms | 84–184ms | 118–217ms | **404 纯文本** |

差距稳定且大（3–5 倍），且几乎全部落在 TCP+TLS 握手上 —— 即跨境 RTT，正是用户真实感知的部分。四条被实测逼出来的设计约束：

1. **用 GET，不用 HEAD。** 健康节点对 HEAD 同样返回 404（new-api 只注册了 GET）。
2. **必须校验响应体。** `cuberouter.cn` 是活生生的反例：TLS 通、应答快、但不是 cuberouter 节点。判据 = **HTTP 200 且 JSON 里有 `data`**，这样"域名已解析但服务没部署"会被自动判为不可用。
3. **`server_address` 让节点自报家门**（`.com` 报 `https://cuberouter.com`）。用作**软校验**：与实际请求的 URL 不一致时记录告警，**为空时不得拦截**（该字段由运维配置）。
4. **一切持久化按节点 id（`cn`/`hk`），不按 URL。** `test.cuberouter.cn` 计划改为 `cuberouter.cn`；存 URL 会让域名一换、所有人的线路记忆全部失效。

## 3. 数据与配置

| 东西 | 存哪 | 理由 |
|---|---|---|
| **节点表**（id → URL） | 构建期注入（env → edition manifest），运行期可被 `config.yaml` 覆盖 | 是产品配置而非用户配置；本地开发要能改 |
| **当前线路** | `config.yaml` 的 `cuberouter.baseUrl`（**F1 的槽位**） | 用户可见、可检查；也是 F1 的直接用途 |
| **`用户名 → 节点 id`** | app 数据库（后端），新表 | 是运行时簿记，不是用户配置，不该随配置导出 |

节点表格式：`MEMMY_CUBEROUTER_NODES=cn=https://cuberouter.cn,hk=https://cuberouter.com`，`config.yaml` 里的覆盖键为 `cuberouter.nodes`（与"当前线路" `cuberouter.baseUrl` 是两个键，不要混）。**节点显示名不进节点表**，走 i18n（`account.node.cn` / `account.node.hk`，未知 id 回落到 id 本身）—— 表里放中文，英文界面就没法用了。

**优先级：`MEMMY_CUBEROUTER_URL` 显式设置时 = 钉死该地址、完全关闭探测**（本地开发与测试的现有行为不变）。节点表缺省时行为与今天一致（回落 `http://127.0.0.1:3000`）。

**探测与选路都在后端**（Electron 主进程，与 `config.yaml` 的读写同侧）；前端只经本地 API 读取探测结果、提交用户选择，自己不直连任何节点。

**F1 成为地基**：本设计的"当前线路"就存在 F1 要引入的那个槽位里，所以 F1 是先决条件、第一步做（优先级 env > config.yaml > 默认值）。

## 4. 探测

- **目标**：`GET <node>/api/status` —— 公开接口，adapter 已有同名调用（`getRegistrationRequirements()` 读的就是它），不新增协议面。
- **方式**：**两边并行发出，等两边都落地或超时（2s）**，不做"先到先得"——先到先得会把网络抖动当成结论，而我们有能力把两边都量出来。
- **取样**：每边发 **2 次**，取两次的中位数作为该节点的 TTFB。单次取样不足以支撑"2 倍差距"这个判据（实测单次波动可达 ±40%）。
- **判据**：HTTP 200 + JSON 含 `data` → 可用；否则视为不可用（含连接失败、超时、纯文本 404）。
- **产物**：可用节点集合 + 各自的 TTFB 中位数。

## 5. 选路规则

1. 只有一个节点可用 → 用它（**不做延迟比较**）。
2. 两个都可用 → **延迟优先**：TTFB 差距 ≥ 2 倍时取快的；差距在 2 倍以内视为接近，用语言兜底（`zh-CN` → 大陆，其它 → 香港）。
3. 都不可用 → 降级为手动选择（见 §8）。

延迟优先而非语言优先，依据是实测：大陆节点快 3–5 倍，而应用只有 `zh-CN` / `en-US` 两种语言 —— 纯语言规则会把"在大陆、用英文界面"的用户送到香港节点绕远路。语言只在两边接近时才作为先验。

## 6. 注册

1. 认证卡片挂载时**后台探测**；未出结果前注册按钮禁用，显示「正在检测线路…」。
2. 出结果后显示「将注册到：大陆」，**可手动改**（下拉展示全部可用节点；全不可用时展示全部节点供硬选）。
3. 用户选定的节点 id 随注册请求一起提交，注册成功后写入 `config.yaml` 的 `cuberouter.baseUrl`，并记入 `用户名 → 节点 id`。

因为选完即定终身，让用户在**账号产生之前**看到并有机会改，是这里唯一诚实的做法。

## 7. 登录

尝试顺序：**记住的节点 → 探测选中的节点 → 另一个节点**（去重后最多试 **2 个**节点）。

- 每次失败（连不上、超时、被拒）都继续下一个，**最多两次尝试、不重试**，避免撞 new-api 的登录限流。
- 任意一次成功 → 写回 `config.yaml` 的 `baseUrl` + 记入 `用户名 → 节点 id`。
- **触发条件不能是"账号不存在"**：new-api 对"用户不存在"与"密码错误"返回同一句 `用户名或密码错误`（防账号枚举）。所以只能是"失败了就试另一边，谁能成就记谁"；两边都失败时用户看到的仍是今天那句通用提示。
- 副作用：用户输错密码时，凭据会被发往两个节点（同一运营方，已确认可接受）。

## 8. 前端

- 注册模式：线路显示 + 下拉（§6）；登录模式不显示线路（登录的节点由记忆和回退决定）。
- 设置页：显示当前线路；**不提供切换按钮** —— 换线路意味着换账号，不是设置项能解决的。
- 探测全失败：显示「无法检测线路，请手动选择」，列出全部节点，并说明所选线路决定账号归属。

## 9. 边界

| 情况 | 行为 |
|---|---|
| 两边都连不上 | 「无法连接服务，请检查网络」（沿用现有文案） |
| 两边都拒绝凭据 | 今天的通用提示，与现在无差别 |
| 跨节点登录成功 | **重新下发模型配置**：新 `apiBase` + 新 key 由成功节点返回（`provisionByokModel` 已有此路径）；旧 endpoint 按 K2 行为保留在 `config.yaml`，不主动清理 |
| 注册要求探测（email/turnstile） | 必须跟随**当前选中的节点**重新读取，不能沿用上一个节点的结果 |
| 域名变更（`test.cuberouter.cn` → `cuberouter.cn`） | 记忆按 id 存，不受影响；只需更新构建期节点表 |

## 10. 测试

- **后端**：节点解析优先级（env > config.yaml > 节点表 > 默认）；探测判据（200+JSON 才算可用、纯文本 404 不算）；选路（单边可用、两边可用且差距大/接近）；登录回退顺序与"成功即记住"；`用户名 → 节点 id` 读写；显式 env 钉死时跳过探测。
- **前端**：注册卡片显示探测结果、可切换、探测未完成时禁用提交；全失败时的手动降级；登录模式不显示线路。
- 全部用假 fetch/假客户端，不打真实网络。

## 11. 落地顺序

1. **F1**：`config.yaml` 的 `cuberouter.baseUrl`（env > config.yaml > 默认）
2. 后端选路与探测（节点表、探测、选路、映射表、登录回退）
3. 前端两张脸（注册卡片、设置页显示）

每步可独立验证。F2（把节点表注入 edition manifest）在本设计中不再是矛盾：真实节点都是 https，manifest 的 HTTPS 校验不再挡路。
